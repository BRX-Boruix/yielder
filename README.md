# yielder

BORUIX 的**调度器压测程序**：不停地让出 CPU，且**永不阻塞**。

[English](README.en.md)

## 做什么

启动后进入循环，反复执行同一个动作：**让出 CPU**。它不计算、不睡眠、不等待任何东西。

它的状态很特殊：

| 状态 | 它是否处于 |
| --- | --- |
| 运行中 | 短暂地 |
| 就绪 | **几乎永远** |
| 阻塞 | **从不** |

## 用来验证什么

**当队列里只剩下一个不停让出的进程时，其他进程还能不能及时响应？**

一个不停让出的进程看起来"很有礼貌"，但如果调度器处理不当，结果可能是其他进程被饿死——它让出后
立刻又是可运行的，调度器可能在它和其他进程之间反复切换，而真正需要响应的进程（如用户正在输入的
`shell`）分不到足够运行时间。本程序是这个场景的最小复现。

## 与 spinburn 的区别

| 程序 | 行为 | 覆盖状态 |
| --- | --- | --- |
| [`spinburn`](https://github.com/BRX-Boruix/spinburn) | 计算后**睡眠** | 多数时间**阻塞** |
| **`yielder`** | 纯让出，**永不睡眠** | 始终**就绪** |

两者检验调度器的不同分支，**合起来才构成完整覆盖**：只测睡眠路径，就碰不到"一直在就绪队列但
不停让位"这条路上的问题。

## 一个排除误诊的判据

系统出现"响应变慢"时，至少有两种可能原因，修复方向完全不同：

| 可能原因 | 修复方向 |
| --- | --- |
| 调度确实不合理 | 改调度逻辑 |
| 统计/记账有偏差 | 改记账方式 |

本程序行为确定、可预测（只让出，无变量），因此它运行时观察到的现象可以更干净地归因，用来区分
这两类问题。

## 用法

拉起后**从外部观察**——检查其他进程是否仍响应及时。它没有输出判定，**永不自行退出**，需强制终止。

```
[yielder] start (pure busy-yield)
```

启动后不再输出：若每次让出都打印，标准输出本身会成为负担，干扰要观测的调度行为。
